# Specs

A spec is the contract between whoever changes the code and whoever writes the tests. Tests are written from
the spec and the public API listing in `api/`, not from the source: the maintainer uses a separate test-writing
session that is mechanically kept from reading the code, and a contributor gets the same effect by writing
the test from the spec row before touching the implementation.

## Layout

| Path | What |
|---|---|
| `docs/specs/<module>.md` | the spec, one per module |
| `docs/specs/api/<module>.txt` | public surface, generated by `python3 tools/api_dump.py <module>`; CI fails when it drifts |
| `tests/test_<module>.py` | tests, one file per module, written from the spec |

## Spec format

```markdown
# <Module>

Status anchored | draft. IDs <PFX>-1 .. <PFX>-n. Tests `tests/test_<module>.py`.

## Purpose

Two lines: what the module is for and which invariant it keeps.

## Public surface

    def select(thumbs, threshold, max_gap)

## Rules

<PFX>-1  What it does, in one sentence, with exact values.
         Why. One line.

<PFX>-2  What happens on empty input, negative numbers, None.
         Why. One line.

<PFX>-3  [hands-on] What is checked only by hand. Evidence: which file or log line proves it.

## Examples

| ID      | Input                 | Result    |
| ------- | --------------------- | --------- |
| <PFX>-1 | [0.0, 0.5, 1.0], 0.5  | [0, 1, 2] |

## Properties

<PFX>-P1 The result is sorted and has no duplicates.

## Errors

What raises and with which type. What never raises. What is swallowed.
```

Rules for writing one.

- IDs are never renumbered. A removed rule keeps its ID with the word "removed".
- Example values are written the way a test sees them, not in words: `[]`, not "empty". Each table row becomes
  one parametrized case, so the row must carry every input the call needs.
- The ID on a row is the rule that row proves. When a row proves two rules, list both.
- A rule a unit test cannot exercise (ffmpeg, files the test writer does not have) is marked
  `[hands-on]` and names its evidence. No test is written for it.
- Status `anchored` means the code exists and a green test is expected. The test must still pin the concrete
  value the spec gives; a test that would also pass on an empty implementation is a defect.
- After writing a spec, one reviewer pass against the code: recompute every example and find what is not covered.
